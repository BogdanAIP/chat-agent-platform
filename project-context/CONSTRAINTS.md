# Constraints

1. Ordinary ChatGPT Chat is the primary and only intelligence/planning layer.
2. Normal product operation must not require OpenAI model API calls or Codex/Work as an additional planner.
3. Standard MCP remains the Chat capability boundary.
4. OpenAI Secure MCP Tunnel + official `tunnel-client` is the accepted ChatGPT reachability path; do not reimplement it.
5. Normal public semantic transport is direct stdio through the secure semantic launcher. 1MCP remains replaceable internal/diagnostic infrastructure, not product identity.
6. Prefer ready-made official/OSS MCP/runtime/API components. Project-owned adapters require a measured missing boundary.
7. No generic project-owned gateway/registry/job/artifact/secret/policy/autonomous-workflow platform unless evidence proves a specific missing boundary.
8. No public inbound port is required for the normal ChatGPT path.
9. Secrets, runtime API keys and tunnel IDs are local operational data and never repository or procedural-skill content.
10. Privileged operations require scoped permissions/negative tests; security must not be interpreted as a blanket ban on useful multi-capability workflows.
11. The target UX must not require one separate ChatGPT app/plugin per local backend.
12. Current accepted public tool names are exactly `workspace_read`, `workspace_write`, `web_open`, `web_observe`, `web_interact`.
13. The five-tool count is a current accepted contract, not a permanent promise. Any expansion decision is explicitly deferred until the Windows desktop surface exists and then requires its own ADR/schema/ordinary-Chat acceptance.
14. Do not preserve the five-tool count by hiding unrelated workflow/desktop operations behind misleading current semantics or a generic opaque dispatcher.
15. Backend registration and backend process activation are separate. Do not run the entire catalog permanently.
16. Multiple backend processes may be active when the actual task requires them.
17. Local models are bounded specialist capabilities, never a second planner. Current accepted target vision path is llama.cpp + LFM2.5-VL-450M F16; future changes remain evidence-driven and replaceable.
18. Procedural memory is guidance/evidence and state, not a second planner or action authorization source.
19. Current observed state outranks remembered procedure. Compiled skills must not use recorded coordinates as the reusable solution.
20. One successful trajectory creates at most a candidate skill. Promotion requires explicit verification/evidence rules.
21. Procedural memory must not persist private chain-of-thought. Store structured/user-visible intent, actions, observations/results and verification evidence only.
22. Raw screenshots/sensitive demonstration content require explicit redaction/retention/deletion policy before long-term storage.
23. A model/Chat completion assertion does not by itself advance procedural state; applicable completion verification is required.
24. A scoped Windows desktop surface is an explicit planned Stage 26.x capability boundary and must not be inferred from browser acceptance or omitted from the roadmap.
25. True arbitrary human “show me once” recording belongs at/after the Windows desktop surface, because the current controlled browser semantic path does not observe arbitrary Windows user interaction.
26. Concrete future local programs/capabilities are chosen from actual user tasks and evidence, not from a fixed precommitted application list.
27. Do not expose arbitrary MCP install/uninstall/update/edit/search/admin controls to ordinary Chat as baseline capabilities.
28. Do not restore legacy code/design because of sunk cost; Git history is archival storage.
29. Avoid new paid infrastructure unless the user explicitly chooses it for a concrete benefit.
30. Real Windows/ordinary-Chat acceptance may only be marked passed from actual target-machine/user-surface evidence.
31. Historical Stage 25 research/handoffs cannot override `START_HERE.md`, `CURRENT_STATE.md`, active Stage 26 contract, current ADRs or current code/tests.
